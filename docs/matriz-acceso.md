# Matriz de acceso · Proyecto OficioYa (Squad 5)
 
El Squad 5 tiene tres microservicios: **Search** (`oficioya-search`), **Reputation** (`oficioya-reputation`) y **Reporting** (`oficioya-reporting`). Todas las peticiones del cliente llegan a través del API Gateway del Squad 1. Roles del proyecto: `TRABAJADOR`, `CONTRATANTE` y `ADMINISTRADOR`.
 
| Endpoint | Roles permitidos | Regla de propiedad o datos ocultos | Código si se incumple |
|---|---|---|---|
| `POST /api/resenas` | `CONTRATANTE`, `TRABAJADOR` | Quien califica sale del token, nunca del cuerpo. Solo puede calificar una parte del servicio, cuando el servicio está cumplido, y una sola vez por servicio. Calificación de 1 a 5 | `401` sin token; `403` para `ADMINISTRADOR`; `404` si el servicio es ajeno o no existe; `409` si ya calificó o el servicio no está cumplido; `400` si la calificación está fuera de 1 a 5 |
| `GET /api/resenas/trabajador/{trabajadorId}` | `CONTRATANTE`, `TRABAJADOR`, `ADMINISTRADOR` | Muestra calificación, comentario, fecha y nombre del autor, sin correo ni teléfono. Las reseñas no se pueden editar ni eliminar | `401` sin token; `404` si el trabajador no existe |
| `POST /api/resenas/{id}/reportes` | `CONTRATANTE`, `TRABAJADOR` | El reportante sale del token. Un usuario no puede reportar dos veces la misma reseña | `401` sin token; `403` para `ADMINISTRADOR`; `404` si la reseña no existe; `409` si ya la reportó |
| `PATCH /api/resenas/{id}/moderacion` | `ADMINISTRADOR` | Solo decide sobre reseñas reportadas (mantener u ocultar); no cambia su contenido. Se registra en log qué administrador, sacado del token, tomó la decisión | `401` sin token; `403` para otros roles; `404` si la reseña no existe; `409` si la reseña no está reportada |
| `GET /api/reputaciones/{usuarioId}` | `CONTRATANTE`, `TRABAJADOR`, `ADMINISTRADOR` | Promedio y número de reseñas. El detalle de penalizaciones y el motivo de pausado solo los ven el propio usuario y el `ADMINISTRADOR` | `401` sin token; `404` si el usuario no existe |
| `POST /api/servicios-calificables` | Ninguno de cliente: solo `oficioya-service` (Squad 4), servicio a servicio | El Gateway no expone esta ruta. Registra servicios cumplidos y cancelaciones tardías (penalización de 0,5). Un usuario no puede invocarla para penalizar a otro | `401` sin credencial de servicio; `403` si llega un token de usuario |
| `POST /api/search` (descripción en lenguaje natural) | `CONTRATANTE` | El texto se valida antes de enviarlo a Gemini. Los resultados no incluyen correo ni teléfono, excluyen trabajadores pausados y se ordenan solo por reputación, nunca por pago | `401` sin token; `403` para `TRABAJADOR` y `ADMINISTRADOR`; `400` si la descripción es vacía o inválida |
| `GET /api/search?oficio=&zona=&tarifaMax=&disponible=&calificacionMin=` | `CONTRATANTE` | Mismas reglas de datos ocultos y orden. Search consulta otros dominios pero no se vuelve dueño de su información | `401` sin token; `403` para otros roles; `400` si un filtro es inválido |
| `GET /api/reporting/reportes?desde=&hasta=` | `ADMINISTRADOR` | Datos agregados (servicios cumplidos, trabajadores pausados, reseñas reportadas), sin datos de contacto. Cada generación se registra en log | `401` sin token; `403` para otros roles; `400` si el periodo es inválido |
| `GET /api/reporting/indicadores` y `/api/reporting/estadisticas` | `ADMINISTRADOR` | Solo métricas agregadas por día, semana o mes | `401` sin token; `403` para otros roles |
| `GET /api/reporting/reportes/exportar?formato=csv\|pdf` | `ADMINISTRADOR` | El archivo exportado nunca incluye contraseñas, hashes ni tokens. Cada exportación se registra en log con el administrador del token | `401` sin token; `403` para otros roles; `400` si el formato no es CSV ni PDF |
 
## ¿Quién emite el JWT y quién lo valida?
 
El JWT lo **emite el dominio Identity del Squad 1** cuando el usuario inicia sesión con su correo y contraseña. El token lleva el correo (`sub`), el rol (`role`), el emisor (`iss`), `iat` y `exp`. Lo **valida primero el API Gateway / Orchestrator del Squad 1**, que es el punto único de entrada desde la aplicación Flutter: rechaza con `401` los tokens ausentes, alterados o vencidos, y bloquea `/api/reporting/**` a quien no sea `ADMINISTRADOR`. Los microservicios del Squad 5 (Search, Reputation y Reporting) **vuelven a validar el token** con su propio filtro, como el `JwtAuthenticationFilter` de este laboratorio, y aplican con `@PreAuthorize` las reglas de rol y de propiedad de la tabla. Así no confían a ciegas en una petición que llegue saltándose el Gateway. Las llamadas internas, como la de `oficioya-service` a Reputation, usan credenciales de servicio y no tokens de usuario.
 
La clave **no se guarda en el repositorio**. Cada componente que firma o valida la recibe por la variable de entorno `JWT_SECRET`: en local desde un `.env` ignorado por Git, como en este laboratorio, y en despliegue desde los secretos del pipeline de CI/CD o del orquestador de contenedores (por ejemplo, GitHub Actions Secrets o Kubernetes Secrets). Como con HS256 cualquiera que tenga la clave puede crear tokens válidos, la mejora recomendada es pasar a **RS256**: Identity firmaría con una clave privada que solo él conoce, y el Gateway y los microservicios validarían con la clave pública, que se puede publicar sin riesgo (por ejemplo, en un endpoint JWKS).
